## 1. The Project

**LaptopFinder Nepal** — an AI-powered laptop shopping assistant for the Nepali market.

- Recommends laptops from a dataset of **5,284 real laptops priced in Nepali Rupees**
- Users give budget + purpose (required) plus optional specs (RAM, storage, brand, CPU/GPU tier, touchscreen…)
- Returns ranked results with prices, specs, human-readable *reasons* ("RTX 4060 fits your gaming purpose") and honest *trade-offs* ("slightly over budget")
- Includes a free-text **Ask AI chatbot** grounded in the dataset so the LLM can never invent laptops or prices
- 100% local/offline: no cloud APIs, no keys, no data leaves your machine

**Where:** `/home/garimadangol/garima`

### File-by-file detail

**`api/main.py`** — The glue between frontend and AI. Endpoints:

| Endpoint | Method | Purpose |
|---|---|---|
| `/recommend` | POST | Budget+purpose+specs → ranked recommendations |
| `/ask` | GET | Free-text query → RAG retrieval of real laptops |
| `/ask-ai` (+`/stream`) | POST | Same retrieval → local Mistral explains results (NDJSON streaming variant) |
| `/brands`, `/purposes`, `/stats`, `/insights` | GET | Metadata & aggregated dashboard data |
| `/log-search`, `/log-click`, `/logs/stats` | POST/GET | Behaviour logging for future collaborative filtering |

Why FastAPI: automatic OpenAPI docs at `/docs`, Pydantic request validation, easy streaming responses.

**`model/recommend.py`** — The heart. Pure-Python ML scoring engine (details in §6). Kept dependency-light so API, UI, RAG and tests all reuse the same logic. Parses fuzzy budgets ("1.5 lakh", "80k") and free-text purposes into canonical labels; engineers CPU/GPU tiers; scores every laptop; returns top-N with reasons + penalties. Falls back gracefully instead of returning nothing.

**`model/rag.py`** — Semantic search layer (details in §7). Indexes every laptop as a natural-language document in ChromaDB; extracts budget phrases like "under 80k" from queries via regex and turns them into hard metadata filters.

**`model/llm.py`** — Talks to Ollama/Mistral. Handles WSL→Windows host discovery (probes localhost, NAT gateway IP from /proc/net/route, resolv.conf nameserver — cached until failure since the gateway IP changes across reboots). All prompting is server-side so no model details leak to the frontend. Streaming supported.

**`api/interactions.py`** — Thread-safe SQLite logging of every search and click. Deliberately separate from recommend.py so the engine stays pure. Purpose: training data for future ML (collaborative filtering / learning-to-rank).

**`frontend/`** — Modern React UI: guided 3-step finder flow, loading skeletons, product detail modals, compare tray with best-value highlighting, Recharts dashboards, per-brand illustrated cards, custom accessible CSS design system.

**`ui/app.py`** — Streamlit prototype. Built first for speed; kept functional as a fallback UI.

**`run.sh`** — Starts uvicorn API on :8000 + Streamlit UI on :8501 in background with logs to /tmp.

## 4. Working Flow (end to end)

### Recommendation flow
```
User picks budget/purpose/specs in React UI (:5173)
        │  JSON
        ▼
POST /recommend → FastAPI validates (Pydantic)
        ▼
recommend(): parse budget → parse purposes → preprocess rows
        ▼
score_laptop() × 5,284 → weighted score + reasons + penalties each
        ▼
rank → top-N (+ fallback if nothing matches)
        ▼
JSON response → React renders cards, modals, comparisons
        │
        └──► /log-search + /log-click → SQLite (future ML training data)
```

### Ask-AI flow (RAG + LLM)
```
User types: "lightweight gaming laptop under 100k"
        ▼
rag.ask(): regex finds "under 100k" → hard price filter in ChromaDB
           query embedded with saved TF-IDF vectorizer
           cosine similarity → nearest real laptops
        ▼
Top-K retrieved spec sheets become THE ONLY context in the prompt
        ▼
Mistral (Ollama) explains those exact laptops — can't invent others
        ▼
Answer streamed back with cited source laptops attached
```

## 6. DEEP DIVE — Machine Learning (the recommender engine)

### What kind of ML this is
**Content-based filtering**: items are described by their own features (price, RAM, CPU/GPU power tiers, purpose labels) and scored against *this user's stated needs*. Chosen because we have rich item features but little user history (that's being collected now via SQLite for future collaborative filtering).

### Feature engineering (where the actual ML work happens)
Raw CSV text is unusable for math, so it gets engineered into numbers:

1. **CPU tier (1–6)** — regex maps hundreds of CPU names onto one engineered power scale: Celeron/Atom ≈ 1–2, Core i3/Ryzen 3 ≈ 3, i5/Ryzen 5 ≈ 4, i7/Ryzen 7 ≈ 5, i9/HX/workstation ≈ 6.
2. **GPU tier (1–6)** — same idea: integrated HD/Iris/UHD ≈ 1–2, MX-series ≈ 3, GTX 1650 ≈ 4, RTX 3060 ≈ 5, RTX 4070+ ≈ 6.
3. **Purpose labels** — free text ("studying", "AI", "editing", "Gaming and Programming") normalized into 10 canonical labels; multi-purposes become sets.
4. **Budget parsing** — "80k", "1.5 lakh", plain numbers → NPR integer.

### The scoring function (`score_laptop`, recommend.py)
Each laptop gets one blended 0–100 score:

```
score = 0.35 × budget_score      # price/budget ratio curve:
                                 #   ≤ budget & ≥60% of budget → 100 ("great value")
                                 #   way under budget → lower ("may be lower spec")
                                 #   ≤15% over → still considered, penalized
                                 #   >30% over → near-zero + explicit penalty
      + 0.25 × purpose_score     # % overlap between user purposes and laptop labels;
                                 # non-match scores 20 (soft penalty), not zero
      + 0.35 × specs_score       # average of RAM/storage/CPU-tier/GPU-tier/brand
                                 # sub-scores vs user minimums
      + 0.05 × balance_score     # rewards matched CPU↔GPU pairing;
                                 # tier gap costs 15 pts/step (bottleneck detection)
```

**Key design choices:**
- **Soft scoring, not hard filtering** — a laptop 10% over budget or slightly under-specced isn't excluded; it's penalized and its trade-offs are shown honestly in the UI.
- **Explainability built-in** — every result ships machine-generated reasons and penalties alongside the number.
- **Graceful fallback** — if nothing fits, constraints relax progressively so users get closest alternatives rather than an empty page.

### Where more ML lives in the stack
- **TF-IDF** (also scikit-learn): classic ML text vectorization powering RAG — detailed below.
- **Future**: logged searches/clicks feed collaborative filtering ("users who liked X also liked Y") and learning-to-rank models once behaviour data accumulates.

## 7. DEEP DIVE — RAG (Retrieval-Augmented Generation)

### The problem RAG solves
An LLM asked "best gaming laptop under 100k?" will confidently invent models and prices (hallucination) because it has no access to our dataset and doesn't know Nepali market prices. **RAG flips generation into retrieve-then-generate**: the model may only speak about documents we hand it.

### Indexing phase (`python3 -m model.rag`)
1. Each of the 5,284 laptops becomes a natural-language document via `build_document()` — e.g. *"ASUS Intel laptop. Core i7 8550U processor (strong performance, tier 5 of 6)…"* Written in prose so semantically similar questions land near the right laptops.
2. Documents are embedded with **TF-IDF**: each doc becomes a sparse vector where terms are weighted by frequency-in-doc ÷ rarity-across-corpus. Config: max 4,000 features, unigrams+bigrams, sublinear TF. Chosen over neural embeddings (MiniLM/BGE) deliberately: zero downloads, deterministic, instant, fully offline — good enough when documents share domain vocabulary (GPU names, "gaming", "SSD").
3. Vectors + full structured metadata (the complete formatted record) are stored in a **ChromaDB PersistentClient** collection in **cosine space**, batched in chunks of 1,000. Persistence means build-once-reuse-always.
4. The fitted vectorizer is pickled alongside (`vectorizer.pkl`) — critical detail: the SAME vectorizer must embed queries at answer time, otherwise vectors live in different spaces.

### Query phase (`rag.ask()`)
5. Regex extracts budget hints ("under 80k", "below 1 lakh", "up to 50 thousand") → becomes a **hard metadata filter** (`price_npr <= max_price`) in ChromaDB — semantic search handles meaning, structured filtering handles money precisely.
6. Query embedded with the saved vectorizer → cosine nearest-neighbours → top-K real laptops with their similarity scores.

### Grounded generation (`model/llm.py` + `/ask-ai`)
7. Prompt contains strict instructions + ONLY the retrieved spec sheets. The model never sees the open internet and is told to cite exact models/NPR prices from context and admit coverage gaps. Hallucination is blocked **structurally, not by prompt-hoping**: there is literally nothing in context to hallucinate FROM.
8. Response streams back as NDJSON deltas; the cited source laptops are returned alongside the prose.

### Why RAG beats the alternatives here
- **Fine-tuning** Mistral wouldn't guarantee factual prices and costs GPU time; RAG guarantees answers come verbatim from retrieved rows.
- **Keyword search alone** misses paraphrases ("light gaming machine" vs "Gaming"); vector similarity catches them.
- **Composability**: the same retrieval feeds both the deterministic `/ask` endpoint and the generative `/ask-ai` chatbot, and both are covered by tests (`test_rag.py`, `test_llm.py`).
